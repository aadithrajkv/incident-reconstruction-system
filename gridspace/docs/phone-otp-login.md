# India mobile OTP accounts

Updated 2026-11-22. Implemented locally; hosted SMS and browser end-to-end verification are not complete.

## Account model

The only welcome-screen sign-in method is an Indian (+91) mobile number and a six-digit OTP. First-time and returning users use the same form. Supabase Auth owns the phone identity; the application owns data through the stable Auth UUID. `public.profiles.username` is a unique, random pseudonym generated by Postgres and visible/copyable in the account dialog. It is not derived from the phone number and is not an authentication or recovery secret.

A phone number cannot be made irreversibly anonymous while still expecting an SMS provider to deliver codes to it. The public profile and posts do not contain the phone number. Supabase Auth and the SMS provider necessarily process it. The Supabase SDK also persists its authenticated session on the device; do not promise that the number never exists in browser session data. Never log OTPs or use phone numbers as advertising identifiers.

The pre-send notice says the number is used for sign-in, recovery and security, is not displayed on posts, and is not used for marketing. The user must acknowledge that notice before sending. This short notice does not replace the product's full privacy policy, provider disclosures and retention decisions, which still need to be finalized before a customer trial.

Returning with the same verified phone restores the same Auth UUID and existing activity. Losing browser storage does not erase server content. Losing access to the number is a separate recovery problem: a copied username is not proof of ownership. Phone reassignment and SIM takeover remain risks. Plan verified number-change support and optionally a linked recovery method/passkey before relying on SMS for valuable merchant accounts. Google OAuth is deferred; if introduced, link it to the existing account rather than silently creating a second one.

## Backend requirements

Apply `20261122120000_phone_accounts_and_business_submissions.sql` to the selected staging project before publishing this frontend. `ensure_phone_account()` checks the server-side Auth record for a confirmed Indian phone, grants the shared-data membership used by the existing restrictive RLS policies, and returns only the username. The browser's `phoneAuthEnabled` flag does not enable hosted Phone Auth or send SMS by itself.

For an existing anonymous session, the app uses `updateUser({phone})` followed by a `phone_change` OTP verification. This requires manual identity linking in hosted Auth settings. The existing Auth UUID and owned rows remain. Verifying the number invalidates the former anonymous restore key. If the number already belongs to another account, the app does not automatically merge, delete or transfer data; a separately designed support flow is required. Anonymous restore SQL is retained for legacy migration, but its login options are removed from the welcome screen.

## SMS setup still needed

1. Choose a Supabase-supported SMS provider and approve its destination-specific cost and trial budget. Configure provider secrets in Supabase, never in `auth-config.js`.
2. Enable Phone Auth and require phone confirmation in the selected staging project. Enable manual linking if migrating anonymous users.
3. Configure CAPTCHA in Supabase and place only the public Turnstile site key in `auth-config.js`. The frontend and hosting CSP already support Turnstile.
4. Restrict SMS destinations to India at the provider/Auth layer, configure server-side rate limits, and establish spending controls. The browser's +91 field and 60-second resend timer cannot prevent direct requests to the Auth API.
5. Validate any India sender/template requirements with the selected provider. Test delivery and wrong/expired code behavior on real devices before inviting customers.
6. Deploy the current Edge Functions with exact allowed origins, then perform the two-account acceptance checklist in `PRODUCTION_TRIAL.md`.

## Local development and verification

`npm ci`, then `npm test` and `npm run build`.

Database tests use embedded PostgreSQL and modeled Auth/Storage schemas to apply every migration and exercise RLS under distinct users. Browser/Auth tests mock Supabase SDK responses. These checks do not replace GoTrue, SMS, real Storage signed URLs or browser tests against staging.

The local Supabase configuration contains two fixed-code Indian test fixtures: `+919000000001` / `246810` and `+919000000002` / `135790`. These are local-only test inputs, not numbers to contact. Do not send real SMS to them or copy this configuration into production. The placeholders for Twilio are intentionally non-working. To exercise local GoTrue, start the local Supabase stack and point the frontend at its local URL/public key; the current config still points to the hosted project. Docker was not running during this implementation.
